Three things are the same everywhere: `nen` (installed and bound by the warm-up), `git` and `gh` authenticated as you, and a `nen/contract.json` in the repository you point Hatsu at. That contract is the only thing Hatsu asks of your project. A `python3` on the host is a prerequisite on the installed plugin path.

<SourceStamp />

## 1. A checkout you keep

Every surface is served from one git checkout of the Hatsu repository. Claude Code links it in place, Antigravity links its generated plugin, Codex copies it per version through its plugin install, and Cursor links each skill into it. Keep the checkout on `main`: whatever it holds is what every session serves.

## 4. The first request, and what happens next

A request runs the loop in an isolated effort worktree and commits locally; nothing is pushed. When you decide the branch goes up, call the push phase; then the PR phase runs review, impacted tests, coverage and opens one PR, and the readiness watch drives it to Ready. The merge is yours, in GitHub. The [Concepts](/docs/concepts/) page explains the loop and the gates; the [Hatsu guide](/docs/hatsu-guide/) lists every skill.
